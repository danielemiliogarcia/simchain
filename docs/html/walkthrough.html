Setup
STEP 0

Start the stack

one command, then wait for height 204

From the repository root:

./scripts/fresh-chain.sh --profile all-tools

This wipes any previous chain volumes and boots a brand-new chain with every optional tool enabled, so nothing later in this walkthrough is missing. First run also builds the images.

Three Bitcoin nodes, a mining controller, a spammer, a control plane, three network agents, and the explorer stack. The mining controller bootstraps the chain to height 204 — coinbase maturity plus a funded address — before it settles into its normal block cadence. Watch it with docker compose logs -f btc-simnet-mining-controller.

Simchain ships several stack sizes. This walkthrough assumes all-tools; the smaller ones exist for CI:

ProfileContainersWhat it adds
docker compose up (minimal)53 nodes + mining controller + spammer. A live chain, nothing to drive it.
minimal-api6+ control plane: CLI, HTTP API, MCP, jobs, scenarios
minimal-organic-reorg9+ network agents: partitions and organic reorgs
basic9the full local stack
all-tools13+ electrs and the mempool.space explorer
fresh-chain.sh always starts from block 0 and destroys the chain you already have. To resume an existing chain instead, use docker compose --profile all-tools up -d.

The network
STEP 1

Mainnet-like network shape

why there are three nodes and not one

Plain regtest gives you one node that mines on demand. Simchain gives you three Bitcoin Core nodes in a full P2P mesh, with the roles deliberately separated:

  • node1 — never mines, wallet disabled, txindex on. This is your endpoint on localhost:18443, standing in for a third-party node you don't control.
  • node2 — a miner with a wallet, exposed on localhost:28443.
  • node3 — a miner with no host port at all, reachable only inside Docker.

The important part is that node1 refuses to be your accomplice. Ask it for a block:

curl -sS --user foo:rpcpassword \
  --data-binary '{"jsonrpc":"2.0","id":1,"method":"getblockcount","params":[]}' \
  http://127.0.0.1:18443/

curl -i --user foo:rpcpassword \
  --data-binary '{"jsonrpc":"2.0","id":2,"method":"generatetoaddress","params":[1,"bcrt1qexample"]}' \
  http://127.0.0.1:18443/
The first call returns a height. The second returns HTTP 403 Forbidden — Bitcoin Core's own per-user rpcwhitelist rejecting it, not a proxy in front of it. Mining, mock time, chain-choice and node-administration calls are all denied on node1.
Your application cannot accidentally mine its way out of a test. If your code needs a block to appear, it has to wait for one like it would on mainnet — which is exactly the class of bug that only shows up in production.

The same credentials are unrestricted on node2, so the walkthrough can still mine on demand:

docker exec btc-simnet-node2 bitcoin-cli -regtest \
  -rpcuser=foo -rpcpassword=rpcpassword getblockcount

STEP 2

Watching the chain

keep one of these open for the rest of the tour

Open a second terminal pane and leave a watcher running. Either of these works:

# block-by-block feed, prints a banner on reorgs
./scripts/chainwatch.sh

# aggregate chain + worker status, refreshed
cargo run -p simchainctl -- status --watch
A block every few seconds once bootstrap finishes, alternating between miners. status additionally shows each node's height and tip, the mining and spam workers' desired vs effective state, the mempool, and a generation counter you will watch increment in the next steps.
Almost every later step is judged by what these panes do. The reorg, partition and degrade steps are only interesting if you can see them happen live.

Configuration
STEP 3

Boot config, and its one trap

.env is genesis-only, on purpose

Compose boot settings live in .env — images, credentials, host ports, node policy, wallet names, and the initial mining and spam policy. Every one has a default, so the stack runs with no .env at all. 

BLOCK_INTERVAL_MODE=fixed
BLOCK_INTERVAL_MEAN_SECS=30
ENABLE_SPAM=false
USER_ADDRESS=bcrt1q...     # funded 2x50 BTC during bootstrap

Now try the thing everyone tries: edit one of those values and restart.

# edit .env, then:
docker compose --profile all-tools up -d
Nothing changes. Same cadence, same spam behavior.
The control plane copies mining and spam policy into state.json on its first ever boot and treats that file as authoritative from then on. Restarts replay state.json, not .env. This is not a bug to work around — it is why a running chain needs a real control surface instead of a restart, which is Step 4.

If you genuinely want to re-read .env, reset only the control plane's own memory. The chain is untouched:

docker compose stop btc-simnet-control-plane
docker volume rm btc-simnet-control-state
docker compose --profile all-tools up -d btc-simnet-control-plane
Height and mempool never move — no node container was restarted — but the workers pick up the new values immediately as the control plane reseeds and reconciles.
That reset discards your policy history, never your chain. Note the second configuration layer: once state.json exists, it — not .env — owns live mining and spam policy.

STEP 4

Live hot-reload, and reproducible mining

the CLI, and the first real retune

Everything from here is done on the running chain. Look first:

cargo run -p simchainctl -- config show

Then change the block cadence from boring-and-fixed to Poisson, like real mining:

cargo run -p simchainctl -- config set \
  BLOCK_INTERVAL_MODE=poisson \
  BLOCK_INTERVAL_MIN_SECS=5 \
  BLOCK_INTERVAL_MEAN_SECS=8 \
  BLOCK_INTERVAL_MAX_SECS=12
Within seconds the pace accelerates and turns irregular in your watcher, and the generation counter increments. No container was recreated and no node restarted.
The control plane owns desired state, applies a complete typed policy to the workers, verifies the effective generation, and rolls back transactionally if any worker refuses. It is compare-and-swap: two people editing concurrently means the stale one gets a 409, not a corrupted config.

For repeatable runs, pin miner selection and the RNG:

cargo run -p simchainctl -- config set \
  MINER_WEIGHTS=node2:1,node3:1 \
  MINING_RNG_SEED=42

And pause the world when you want to act by hand:

cargo run -p simchainctl -- mining pause
cargo run -p simchainctl -- mine --node node2 --blocks 1 --wait
cargo run -p simchainctl -- mining resume
BLOCK_INTERVAL_MEAN_SECS must fall inside [MIN, MAX] or the patch is rejected. When moving the mean outside the current bounds, set all three in the same command — the defaults ship as min 10 / max 20, which would reject a mean of 8 on its own.

Blocks & fees
STEP 5

Realistic block and fee-market pressure

non-empty blocks, and a price floor

Empty blocks are the other great regtest lie. The spammer fills blocks with locally signed raw transactions, keeps the mempool at a configured depth, and maintains an economic fee floor. Turn it up: 

cargo run -p simchainctl -- config set \
  ENABLE_SPAM=true \
  SPAM_FILL_BLOCK_RATIO=3
Blocks stop being empty and the mempool grows a backlog — a ratio of 3 keeps roughly three blocks' worth of transactions queued, so there is always competition for the next block.
The fee floor is built by paying for it, not by editing Bitcoin Core's relay or mempool policy. Simchain's rule is that mainnet behavior is imitated, never configured away — so a transaction that would be rejected on mainnet is rejected here too.

For a controlled spike rather than continuous pressure, provision capacity and then burst:

cargo run -p simchainctl -- mining pause
cargo run -p simchainctl -- spam prepare --node node2 --txs 100 --data-bytes 8000
cargo run -p simchainctl -- spam burst  --node node2 --txs 100 --data-bytes 8000
cargo run -p simchainctl -- mine --node node2 --blocks 1 --wait
cargo run -p simchainctl -- mining resume
The mempool inflates by 100 transactions, then drains into exactly one fat block. --data-bytes selects DATA mode: each transaction carries one OP_RETURN payload of that size, which fills blocks fast without growing the UTXO set.
prepare mines the confirmation blocks for the burst's dedicated capacity; the burst itself never mines. Skip prepare and a burst that runs short of capacity fails outright with a "prepare it first" error rather than half-filling. Swap --data-bytes for --outputs-per-tx N if you want wallet-shaped transactions instead of OP_RETURN payloads.

STEP 6

The faucet

fund your app's address

Miner treasury coins, paid to any regtest address you control:

cargo run -p simchainctl -- faucet --to bcrt1q...=1.5btc --wait

You can pass several --to ADDRESS=AMOUNT pairs in one call. Amounts take decimal BTC (1, 0.25, 1btc) or integer satoshis (25000000sat). Need an address? The dashboard's Faucet tab ships a deterministic BIP84 test wallet with ready-made addresses — see Step 7.

A transaction paying exactly zero fee, confirmed in the next normal block.
A zero-fee transaction is normally unmineable. The miners give this one a virtual priority delta so it gets included — again without touching relay policy. It is a good demonstration of the project's central constraint: change the miner's preferences, never the network's rules.
Safety limits are fixed, not settings: at most 100 outputs and 10,000 vB per transaction, plus a confirmed reserve each miner wallet must retain (FAUCET_WALLET_RESERVE_BTC) and a cap on total value per request (FAUCET_MAX_REQUEST_BTC).

Control surfaces
STEP 7

The dashboard

same operations, in a browser

Open http://localhost:8090/ and tour it top to bottom:

  • Status — chain height, per-node state, miner labels, worker health. The same data as status --watch.
  • Live retuning — change BLOCK_INTERVAL_MEAN_SECS from the UI and watch the generation bump, exactly as in Step 4.
  • Pause / resume workers with a click.
  • Faucet — bootstrap address card — the USER_ADDRESS that received 2×50 BTC during bootstrap.
  • Faucet — regtest test wallet card — a deterministic BIP84 wallet from a public BIP39 mnemonic, with reveal and copy buttons. Copy an address, paste it into the faucet form, fund it from the browser.
  • Jobs — every mine, burst, reorg and partition as a durable server-side job with progress and results.
  • Explorer link — jumps to the local mempool.space instance (Step 16).
Dashboard, CLI, HTTP API and MCP are four adapters over one operation set — one mutation lock, one job coordinator, one source of truth. Nothing you click can drift from what your CI scripts do.
An active-job banner while a job runs. Only one mutation job runs at a time across every surface; a second incompatible request is rejected outright, not queued, because a queued chain mutation can be unsafe by the time it runs.
That test wallet's mnemonic is public and printed in the UI. It exists for regtest only — never send mainnet funds to an address derived from it.

STEP 8

The HTTP API

what the CLI is made of

The CLI is a thin client over a versioned localhost API. Anything you have run so far, your CI can do with curl:

curl -s localhost:8090/api/v1/status | jq .

token="${SIMCHAIN_CONTROL_TOKEN:-simchain-control-dev-token}"
generation=$(curl -s localhost:8090/api/v1/config | jq .generation)

curl -s -X PATCH localhost:8090/api/v1/config \
  -H "Authorization: Bearer $token" \
  -H 'Content-Type: application/json' \
  -d "{\"settings\":{\"SPAM_FEE\":\"0.0005\"},\"base_generation\":$generation}"
  • Reads are open on localhost; mutations require the bearer token.
  • base_generation is the same compare-and-swap the CLI uses — a stale value gets a 409.
  • Other routes worth knowing: /api/v1/jobs, /api/v1/faucet, /api/v1/config/schema.
The API binds to 127.0.0.1 only and rejects any non-loopback Host header, which is what stops a hostile web page from resolving its own hostname to your loopback and driving your simnet. Do not put it behind a public reverse proxy.

STEP 9

MCP — let a coding agent drive

optional, but it is the same operation set again

The control plane speaks MCP over streamable HTTP at http://localhost:8090/mcp, protected by the same bearer token.

Once your editor's agent is connected, ask it in plain language:

"Slow mining to a 20 second mean and tell me the current height."
"Partition node3, mine 5 blocks on it, heal, and report the winning tip."
An agent debugging your wallet code can reshape the chain underneath it — trigger a reorg, add fee pressure, split the network — without you translating each request into commands.

Chain events
STEP 10

Programmatic reorgs

the event your app probably handles worst

Keep your watcher visible, then rewrite recent history on purpose:

cargo run -p simchainctl -- reorg start --depth 2 --node node3 \
  --adds-new-txs 1 --double-spend-pct 1 --wait

cargo run -p simchainctl -- jobs watch
Chain height steps backwards, then replacement blocks rebuild from the live mempool — including one injected transaction and one deliberate double spend. Your watcher prints a reorg banner.
This is the question worth asking of your own code: does it handle a confirmed transaction becoming unconfirmed, or a transaction being permanently replaced by a conflicting one? Better to find out here.

Variations worth trying:

  • --empty mines empty replacement blocks, so orphaned transactions stay unconfirmed — a chaos reorg.
  • --double-spend-pct N permanently drops a share of the orphaned wallet transactions by mining conflicting spends.
  • Continuous mode re-runs a reorg every N blocks, if you want sustained instability.
This is an administrative reorg: invalidateblock is a node-local instruction and does not propagate over P2P, so the coordinator applies it on each node. For a reorg produced by the real mechanism, see Step 12.

STEP 11

True shorter-chain rewinds

a reorg's quieter cousin

A reorg replaces history with a longer branch. A rewind just removes it:

cargo run -p simchainctl -- rewind --blocks 3 --wait
All three nodes land on the same genuinely lower height, with no replacement blocks mined. Transactions from the discarded blocks can return to node-local mempools.
Useful when you want to replay the same block range under different conditions, or to test how your indexer copes with a tip that simply moved backwards.
The job never crosses below bootstrap height 204, persists rollback information before mutating, and uses reconsiderblock to restore the original branch if it fails partway. If an electrs-based profile is active, its disposable index may not follow a rollback-only shape — ./scripts/recover-explorer.sh recreates the indexer and waits for its tip to match node1.

STEP 12

Network splits and organic reorgs

the one worth setting up properly
the network agents — --profile minimal-organic-reorg or richer. all-tools includes them.

Set up your watchers before splitting, or you will only see the aftermath. Node3 has no host RPC port by design, so inject the watcher into the container itself: 

./scripts/inject-tools.sh btc-simnet-node3
# Pane A — connected side (node2, host-exposed RPC)
./scripts/chainwatch.sh -P 28443 -i 1

# Pane B — isolated side, watched from inside the container
docker exec -it btc-simnet-node3 chainwatch \
  -H 127.0.0.1 -P 18443 -u foo -p rpcpassword -i 1

Both panes should agree on height and tip. Now split the mesh:

cargo run -p simchainctl -- partition start --node node3 \
  --main-blocks 3 --isolated-blocks 5 --heal-delay-secs 15
Pane A climbs by 3 blocks; Pane B climbs by 5. Different heights, different tips, same starting point — two real, independently valid Bitcoin chains growing at once. The --heal-delay-secs hold keeps them apart long enough to actually look at.
When the hold ends the job heals the split by itself. Because isolated-blocks (5) is greater than main-blocks (3), node3's branch has more work: Pane A jumps up to node3's height and prints a reorg banner, while Pane B stays quiet — it was already on the winning tip.
That is an organic reorg: nobody instructed any node to abandon a branch. The nodes chose the most-work chain themselves, which is what actually happens on mainnet.

Bitcoin Core remembers the losing branch. Ask it afterwards:

docker exec btc-simnet-node1 bitcoin-cli -regtest \
  -rpcuser=foo -rpcpassword=rpcpassword getchaintips
Only P2P traffic is cut — control traffic rides a separate Docker network, which is why you can watch both sides throughout. If you forget the watcher panes, getchaintips still shows the losing branch as a valid-fork entry afterwards.

STEP 13

P2P link degradation

slow and lossy, without touching RPC
the network agents, same as Step 12.

Add latency to one node's P2P egress, then mine on that node while it is impaired:

cargo run -p simchainctl -- degrade start --node node2 \
  --delay-ms 5000 --loss-pct 0 --seconds 30

# while that job reports observing_degraded_network:
cargo run -p simchainctl -- mine --node node2 --blocks 1 --wait
mine returns immediately — RPC is on the separate control network and is never shaped — but node1 and node3 only learn about the new tip about five seconds later, when the delayed P2P announcement lands. In status --watch, node2's height ticks up first and the others visibly lag.
Propagation delay is invisible in normal regtest, where every node learns everything instantly. This is how you test code that assumes all nodes agree on the tip at the same moment.
Impairment is lease-based with a TTL: if the control plane dies mid-job, the agent clears its own qdisc and the link heals. Degradations occupy a per-node lane rather than the global mutation lock, so a manual Mine on the same node may overlap, as may degradations on other nodes.

Repeatability
STEP 14

Declarative scenarios

everything above, as a checked-in file

Open scenarios/all-features-live.yml and read it: every action from this walkthrough as ordered, version-controlled steps with assertions and checkpoints. Run a small one:

cargo run -p simchainctl -- scenario validate scenarios/pause-then-burst.yml
cargo run -p simchainctl -- scenario explain  scenarios/pause-then-burst.yml
cargo run -p simchainctl -- scenario run      scenarios/pause-then-burst.yml \
  --result results/burst.json
Steps tick through while the chain reacts in your watcher. The server validates the whole document before reserving the mutation coordinator, waits for height 204, and persists step events and results.
This is the CI story. Scenarios are durable server-side jobs: disconnecting the client does not cancel the run, and named checkpoints let a CI job block on an exact chain state, run external assertions against it, then release by generation.
A scenario containing partition or degrade steps needs the network agents. On a stack without them the whole scenario is rejected at submission with a 503 naming the profile to start — deliberately, so it cannot fail halfway through after already mutating the chain. Set restore_settings: true to durably capture and auto-revert the config map afterwards.

STEP 15

Chain snapshots

stop paying the bootstrap cost

Save the state you just built, then get back to it instantly:

./scripts/snapshot.sh save after-walkthrough
./scripts/snapshot.sh list
./scripts/snapshot.sh restore after-walkthrough --profile all-tools
A restore brings back blocks, chainstate, miner wallets, the mempool and the recorded Compose profile — not just the block height.
Every fresh start otherwise re-mines to height 204 before anything interesting can happen. A snapshot turns a known-good starting state into a fixture you can hand to a test suite.
Take snapshots from a live stack, and let a shutdown finish on its own — force-killing bitcoind mid-write can corrupt the chainstate you were trying to preserve.

STEP 16

Plugging your application in

the point of all of the above

Four ways in, all pointed at node1 — the node you do not control:

InterfaceEndpointFor
Bitcoin Core RPClocalhost:18443wallets, custody systems, anything speaking Core RPC
ZMQ28332–28336LND / CLN, indexers, watchers — all five topics
Electrum RPClocalhost:60001Electrum-protocol clients, via electrs
Explorerlocalhost:1080a local mempool.space following node1

All five ZMQ topics are published — rawblock, rawtx, hashblock, hashtx and sequence. The last is the reorg-aware one: it reports mempool add/remove and block connect/disconnect, so a consumer can follow the events from Steps 10–12 correctly.

Go back and re-run any chaos step with your own application attached. A reorg your code has never seen is the whole reason this project exists.
electrs maintains a disposable index. After a rewind or a deep reorg it may need ./scripts/recover-explorer.sh to rebuild and catch up with node1.

DONE

Where to go next

You have run every feature Simchain has. A short recap of the shape:

  • .env boots it → the CLI retunes it live → the API automates it → the dashboard makes it visible → jobs break it on purpose → scenarios make it reproducible → MCP hands it to agents.
  • All four surfaces are adapters over one operation set, one mutation lock, one source of truth.
  • Bitcoin Core's relay and mempool policy is never modified. Mainnet behavior is imitated, not configured away.

Tear down when you are finished — the chain survives on named volumes and resumes on the next up:

docker compose --profile "*" down

# or discard the chain too
docker compose --profile "*" down -v
